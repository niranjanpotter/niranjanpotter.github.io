Q4 Q4 JWT Bearer vs Username-Password auth for Salesforce — which do you use?
✅ Answer

Username-Password: requires actual user credentials. Password changes break integration, account

can lock, appears as user in audit logs — never use in production.

JWT Bearer: RSA asymmetric key pair — no password needed. Token signed by MuleSoft private key,

validated by Salesforce with uploaded public key. Survives password changes, cleaner audit trail

showing Connected App not a user.

⚠ ALWAYS USE JWT BEARER IN PRODUCTION

Generate RSA key pair → upload public cert to Connected App in Salesforce Setup

Store keystore.jks as Secure Property (AES-CBC encrypted) in CloudHub

Rotate keys: upload new cert BEFORE removing old one (zero-downtime rotation)

Q5 Q5 What is an External ID in Salesforce? How is it used in Upsert?
✅ Answer

A custom field with "External ID" checkbox enabled in Salesforce Setup. Stores source system ID (SAP

Customer Number). For Upsert: Salesforce finds records matching this field — found → update, not

found → insert.

In MuleSoft: set externalIdFieldName="SAP_Customer_ID__c" on the Upsert operation. Makes

integrations safe to retry without creating duplicates.

Q2 Q2 What is event retention? What if Mule app is down >72 hours?

Subscribe · Publish · replayId · 72-hour retention · Duplicate handling

✅ Answer

Salesforce Platform Events and CDC are retained for 72 hours. If MuleSoft subscriber restarts with

replayId="-2" , it receives all events from the last 72 hours — nothing is lost for normal downtime.

If downtime exceeds 72 hours: those events ARE permanently lost. Mitigation: also publish to

Anypoint MQ (7-day retention) as backup fan-out for critical events. Or implement a Scheduler that

queries Salesforce directly for records modified during the downtime window using LastModifiedDate

> :lastRun watermark.

Q3 Q3 How do you handle duplicate Platform Events (at-least-once delivery)?
✅ Answer

Salesforce uses at-least-once delivery — duplicates are possible. Implement idempotency with

ObjectStore:

Idempotency Pattern

/- 1. Extract Replay ID or business key from event

/- 2. Check ObjectStore

os:contains(key=replayId, objectStore=idempotency-store)

/- EXISTS → skip and ACK

/- NOT EXISTS → process → os:store(key, TTL=72h) → ACK

Use acknowledgementMode="MANUAL" so ACK only happens after successful ObjectStore write +

processing.

Q1 Q1 Explain the Salesforce JWT Bearer authentication flow step by step.
✅ Answer
  • 1. Create a Connected App in Salesforce Setup
  • 2. Generate RSA key pair: openssl genrsa -out private.pem 2048 → create cert from public key
  • 3. Upload the public certificate to Connected App
  • 4. Configure MuleSoft Salesforce Connector with Consumer Key, keystore path, key alias, and

username

  • 5. MuleSoft builds JWT claim: issuer=ConsumerKey, sub=SF_username, aud=login.salesforce.com
  • 6. MuleSoft signs JWT with private key → sends to Salesforce token endpoint
  • 7. Salesforce validates signature using uploaded public cert → returns access token (1hr validity)
  • 8. MuleSoft auto-renews token before expiry — no manual refresh needed

✅ WHY JWT OVER USERNAME-PASSWORD

No passwords stored anywhere — survives Salesforce password policy changes

Token auto-renews every 1 hour — no integration downtime

Audit logs show Connected App name, not a user login — cleaner security audit

Q2 Q2 How do you rotate the JWT signing key without downtime?
✅ Answer

Salesforce supports multiple active certificates on a Connected App. Rotation process:

  • 1. Generate new RSA key pair
  • 2. Upload new public cert to Connected App — keep old cert active
  • 3. Deploy updated MuleSoft config pointing to new keystore
  • 4. Wait for all in-flight tokens using old cert to expire (max 1 hour)
  • 5. Remove old cert from Connected App

Zero downtime because Salesforce accepts tokens signed by ANY active certificate simultaneously.

Q3 Q3 Can the same Connected App be used across multiple environments?
✅ Answer

Technically yes — but best practice is separate Connected Apps per environment (sandbox,

production). Reasons: different Salesforce orgs have different URLs; separate apps allow independent

In MuleSoft: use ${aws-s3::config:sf.consumerKey} in property files — different value per

Q3 Q3 How do you handle SQS visibility timeout in MuleSoft processing?
✅ Answer

Visibility timeout is the period a message is hidden from other consumers after being received. If

MuleSoft processing time exceeds this timeout, the message becomes visible again → redelivered →

duplicate processing.

Best practice: Set SQS visibility timeout = at least 3× your Mule processing time. Use MANUAL ack

mode — delete message from SQS only after successful processing. For long-running operations,

extend visibility timeout programmatically via ChangeMessageVisibility API.

Q2 Q2 How do you prevent infinite loops in bidirectional Salesforce↔SAP sync?
✅ Answer

Challenge: updating SAP triggers a Salesforce CDC event which triggers SAP update again — infinite

loop.

Solution 1 — Source System Flag: Add SAP_Last_Updated__c timestamp field to Salesforce. When

MuleSoft updates SF from SAP, set this field = NOW. In CDC subscriber, check: if

SAP_Last_Updated__c was updated within last 5 seconds → skip (it was a SAP-originated update).

Solution 2 — Dedicated Integration User: Use a dedicated Salesforce user

(mulesoft_integration@fpl.com) for all SAP-originated updates. In CDC subscriber, skip events where

commitUser == 'mulesoft_integration@fpl.com' . This breaks the loop at the event source.

Q3 Q3 How do you handle SAP being down when a Platform Event arrives?
✅ Answer

Synchronous flows: Until Successful with 3 retries + 30s delay. After exhaustion → On Error Continue

→ update Salesforce with SAP_Error_Status__c = 'FAILED' → Anypoint Alert to ops team.

Asynchronous flows (preferred): Publish the Platform Event payload to Anypoint MQ — messages

persist (7-day retention) and process when SAP recovers. MQ consumer checks ObjectStore

idempotency key before each attempt to prevent duplicate SAP orders on retry.

Q2 Q2 What is MANUAL acknowledgement mode? Why do you use it?
✅ Answer

In AUTO mode: message is ACKed immediately on receipt — if processing fails, message is

permanently lost. In MANUAL mode: you explicitly call anypoint-mq:ack after successful processing

MANUAL ACK Pattern

After max delivery attempts: message moves to Dead Letter Queue (DLQ) automatically. Ops team

reviews DLQ daily for failed messages requiring manual intervention.

Interview Drill-Down & "What If?" Cross-Questions
"What happens if you use AUTO ack mode and the Mule worker crashes mid-processing?" → The

• message was already ACKed on receipt — it is permanently lost. No redelivery, no DLQ. This is the critical

• reason we NEVER use AUTO ack for important messages. MANUAL ack means the message stays in-flight

• until you explicitly ACK it.

"When exactly does the NACK happen — immediately on error or after retries?" → NACK happens in

• the on-error-propagate error handler — immediately when any uncaught error occurs in the processing

• flow. The message is returned to the queue where it becomes visible again after the visibility timeout. It will

• be redelivered up to the configured max delivery attempts before going to DLQ.

"What is the max delivery attempt count in Anypoint MQ? Where do you configure it?" → Configured

• on the queue definition in Anypoint MQ UI — "Max Redeliveries" setting. Default is typically 10. When this

• count is exceeded, MQ automatically moves the message to the bound DLQ. Always bind a DLQ to every

• queue — without a DLQ, messages that exceed max retries are permanently discarded.

"AUTO ack vs MANUAL ack vs IMMEDIATE — what is IMMEDIATE?" → AUTO = ACKed after subscriber

• receives message. MANUAL = you call ack/nack explicitly. IMMEDIATE = ACKed before subscriber

• processes — message removed from queue before any processing starts. IMMEDIATE is less safe than

• AUTO — use only when you explicitly want fire-and-forget semantics.

  • 3. EXISTS: Log "Duplicate detected" + anypoint-mq:ack + return
  • 4. NOT EXISTS: Process message → on success: os:store(key=transactionId, TTL=25h) + anypoint-

mq:ack

  • 5. On processing failure: anypoint-mq:nack (message returns to queue for retry)

Use persistent=true ObjectStore so idempotency survives app restarts. TTL = slightly more than MQ

message retention period.

Q2 Q2 What is the difference between VM connector and flow reference?
✅ Answer

Flow Reference: Synchronous direct call to another flow in the SAME application. Same thread, same

transaction context. No messaging overhead.

VM Connector: Message-based communication using an in-memory/persistent queue within the

SAME application (VM queues are app-scoped). Can be synchronous (request-reply) or asynchronous

(one-way). Decouples sender from receiver — useful for async processing within one app.

Key difference: Flow-ref is a direct function call; VM is message-based within the app (like Anypoint

MQ but scoped to one application and not durable across cluster).

Q3 Q3 What is fan-in and fan-out? How do you implement them?
✅ Answer

Fan-Out: Send same message to multiple destinations. Implementation: Scatter-Gather (parallel

routes), Anypoint MQ Exchange (one publish → all bound queues get copy), or multiple MQ publish

steps.

Fan-In: Collect results from multiple parallel paths into one. Scatter-Gather automatically fan-in: waits

for all routes, aggregates into an array. For MQ fan-in: use a separate aggregation flow that collects

messages keyed by correlationId with a TTL-based ObjectStore to accumulate all parts before

continuing.

🔹 Security & Connectivity

Q5 Q5 How do you set up HTTPS connection in MuleSoft? One-way vs two-way SSL?
✅ Answer

One-way SSL (server authentication only): Client verifies server's certificate. Server does NOT verify

client. Standard HTTPS. In MuleSoft: HTTP Listener needs tlsContext with keyStore (server cert).

HTTP Request needs tlsContext with trustStore (CA cert to trust server).

Two-way SSL (mutual TLS / mTLS): Both client and server present certificates and verify each other.

In MuleSoft HTTP Request: configure BOTH a trustStore (to verify server) AND a keyStore (client

certificate to present to server). Used for machine-to-machine authentication without

username/password.

Q6 Q6 What is VPC and VPN in CloudHub? What is SLB vs DLB?
✅ Answer

VPC (Virtual Private Cloud): Private isolated network segment in CloudHub where your Mule apps

run. Isolates your apps from other CloudHub customers. Required for DLB.

VPN: Encrypted tunnel connecting your CloudHub VPC to your on-premise data center. Mule apps in

VPC can access internal systems (SAP, databases) via private IP through VPN.

SLB (Shared Load Balancer): Multi-tenant, shared CloudHub infrastructure. Public IPs. Suitable for

lower-security workloads. Free.

DLB (Dedicated Load Balancer): Your own private load balancer in a VPC. Custom domain names,

custom SSL certificates, private IPs. Required for VPN-connected on-premise access. Additional cost

but necessary for enterprise production deployments.

Q11 Q11 What is horizontal vs vertical scaling? When do you use each in MuleSoft?
✅ Answer

Vertical Scaling: Increase vCores per worker (0.1 → 0.2 → 0.5 → 1 → 2 → 4 vCores). More CPU and

memory per instance. Best for CPU-bound or memory-intensive tasks (large DataWeave transforms,

complex aggregations).

Horizontal Scaling: Add more workers (1 → 2 → 4 workers). More instances running the same app in

parallel. Best for I/O-bound tasks (many concurrent HTTP requests, MQ consumers). CloudHub

supports autoscaling — configure min/max workers and CPU threshold.

At FPL: During billing cycle peak load (8-10AM), autoscaling kicks in from 2 to 4 workers on the

billing XAPI. Off-peak: scales back to 2 to reduce cost.

Q13 Q13 If 5 people are invoking the same URL, how does MuleSoft ensure the correct response goes to

each caller?

✅ Answer

HTTP is stateless and request-response. Each HTTP request opens a unique connection/thread. The

HTTP listener binds the response to the original request connection. MuleSoft's thread pool assigns

one thread per request — each thread has its own Mule event context (payload, variables, attributes).

Thread A's response is sent back on Thread A's connection, Thread B's on Thread B's, etc. The HTTP

infrastructure ensures isolation. correlationId (set at start of each request) further tracks each

individual transaction through all layers.

✅ Answer

Query: Returns only active/non-deleted records. Standard SOQL operation. Example: SELECT Id

Q16 Q16 How do you handle SFTP strategies? How do you auto-delete files on SFTP?
✅ Answer

SFTP Strategies: (1) Polling Strategy — trigger when file arrives (Mule SFTP listener with

watermark). (2) Read Strategy — on-demand file read with SFTP Read operation. (3) Write Strategy

— write processed files back to SFTP.

Auto-delete files: SFTP Listener has an autoDelete="true" attribute — deletes the file from SFTP

server after reading. For archiving instead of deleting: use autoDelete="false" and add an SFTP

Move operation after processing to move file to an /archive/ folder with a timestamp suffix. For

purging old files: scheduled Mule flow that lists files older than N days via SFTP List and deletes them

with SFTP Delete.

Q17 Q17 In a Bulk Insert with 10 records, if record 7 is invalid, what happens?
✅ Answer

This depends on the connector and database.

Database Bulk Insert (non-XA transaction): All 10 records are sent in a single batch. If record 7 fails

validation at the database, the entire batch is typically rolled back — 0 records inserted. This is

database-level atomic behavior.

Salesforce Bulk Insert: Partial success is possible — Salesforce processes all records and returns

individual success/failure results. Records 1-6 and 8-10 may succeed while record 7 fails. Retrieve

results via Bulk API result polling.

Solution for guaranteed partial processing: Use Batch Job — each record processed individually.

Record 7 fails, recorded in failedRecords, records 1-6 and 8-10 succeed. Total failures tracked in On

Complete.

Q18 Q18 An exception arose at System layer and I want that error message to propagate to Experience

layer. How?

✅ Answer

Use on-error-propagate at each layer. In the SAPI: catch the error → build standardized error

payload → re-throw using . In the PAPI: same pattern — on-error-propagate re-throws the error

upward. In the XAPI: on-error-propagate catches it → formats into the standard HTTP error response

format with correct status code.

The key: keep the error payload consistent at every layer. Use a standard error schema {correlationId,

errorCode, message, layer} so XAPI always knows what to expect regardless of which layer the error

originated from.

Q19 Q19 System API is taking too long to respond (timeout). How do you fix it from XAPI's perspective?
✅ Answer

Three approaches depending on requirements:

  • 1. Increase responseTimeout: On the HTTP Request config in PAPI that calls SAPI, increase

responseTimeout value. Quick fix but doesn't solve the root cause.

  • 2. Async pattern (preferred): XAPI returns 202 Accepted immediately. PAPI publishes request to

Anypoint MQ. MQ consumer calls SAPI when it's ready. XAPI provides a polling endpoint or callback

URL for the result.

  • 3. Retry with Until Successful: Wrap the SAPI call in Until Successful — if timeout occurs, retry up to

N times with a delay. Catch MULE:RETRY_EXHAUSTED → return 503 with Retry-After header to caller.

Q5 Q5 What is guaranteed delivery? How do you ensure it in MuleSoft?

Guaranteed delivery ensures messages are reliably delivered even if the system crashes or restarts.

Q6 Q6 After batch job processes 1,000 of 10,000 records and restarts, how do you avoid reprocessing?
✅ Answer

Multiple strategies work together:

  • 1. Batch Persistence (built-in): Mule Batch Job is persistent by default — if the runtime restarts, it

resumes from where it left off IF using a persistent object store. Ensure persistent=true on the

batch job's underlying store.

  • 2. Watermarking: Store last-processed record ID in persistent ObjectStore. On restart, read

watermark and query only records with ID > lastProcessedId.

  • 3. Status Column in DB: Add a processed=true/false column. Before processing each record,

check if already processed. Batch step: accept expression filters out processed=true records.

  • 4. Idempotent processing: Use UPSERT instead of INSERT — if the same record is processed twice,

the second time just updates the existing record without creating a duplicate.

Q6 Q6 After batch job processes 1,000 of 10,000 records and restarts, how do you avoid reprocessing?
✅ Answer

Multiple strategies work together:

  • 1. Batch Persistence (built-in): Mule Batch Job is persistent by default — if the runtime restarts, it

resumes from where it left off IF using a persistent object store. Ensure persistent=true on the

batch job's underlying store.

  • 2. Watermarking: Store last-processed record ID in persistent ObjectStore. On restart, read

watermark and query only records with ID > lastProcessedId.

  • 3. Status Column in DB: Add a processed=true/false column. Before processing each record,

check if already processed. Batch step: accept expression filters out processed=true records.

  • 4. Idempotent processing: Use UPSERT instead of INSERT — if the same record is processed twice,

the second time just updates the existing record without creating a duplicate.

🔹 Performance Tuning

Q9 Q9 How do you tune MuleSoft application performance?
✅ Answer

Rule #1: Measure first. Change one thing at a time. Baseline → change → retest.

maxConcurrency on flows: caps parallel events. At limit → back-pressure → HTTP 503. Set to

match downstream capacity.

DB pool maxPoolSize: default 5. If flow concurrency > pool size → queue builds up → latency

spikes. Tune to match expected concurrency.

Scatter-Gather: parallel calls to different APIs — 55% response time reduction vs sequential at

FPL

Repeatable file store buffer: default 512KB before disk. Increase for large payloads staying in

memory.

DataWeave optimization: select specific fields early ( $select ), use groupBy for lookups

instead of nested filter loops

Scale horizontally (add workers/replicas) for I/O-bound flows. Scale vertically (add vCores)

for CPU-bound transforms.

⚠ COMMON PERFORMANCE ANTI-PATTERNS

DB pool size smaller than flow maxConcurrency → queue builds → timeouts

Logging large payloads at INFO in production — serialize cost + log volume

One HTTP call per item in ForEach — use bulk APIs or Parallel ForEach instead

Storing large streaming payloads in vars — use non-repeatable streaming instead

S2 S2 SCENARIO: You have a Mule app deployed on CloudHub with 2 workers. An MQ message is

processed by Worker 1. Worker 1 crashes mid-processing. What happens?

✅ Complete Scenario Answer

With MANUAL ack mode (correct setup): The message was never ACKed because processing

didn't complete. Anypoint MQ's visibility timeout expires → message becomes visible again →

Worker 2 (or restarted Worker 1) picks it up → processes it. The message was NOT lost.

The idempotency problem: Worker 1 may have partially processed before crashing. Worker 2

will process the same message again. Without idempotency, this causes duplicate writes. With

ObjectStore idempotency check (persistent=true, Anypoint OS v2), Worker 2 sees the

transactionId already stored → skips as duplicate → ACKs safely.

Interview Drill-Down & "What If?" Cross-Questions
"What if you used AUTO ack mode?" — Message is ACKed immediately when received by Worker

• 1. When Worker 1 crashes, message is permanently lost — no redelivery. This is why we NEVER use

• AUTO ack for critical messages.

"How does Anypoint OS v2 help here?" — In-memory ObjectStore data on Worker 1 is lost with

• the crash. OS v2 is a cloud-side persistent store — shared across all workers and survives restarts.

• Worker 2 can see transactionIds stored by Worker 1.

"What if the crash happens BETWEEN the os:store and the anypoint-mq:ack?" — Message is

• redelivered. OS v2 has the key stored, so Worker 2's idempotency check detects it → safe skip + ACK.

• This is the exact race condition idempotency handles.
S3 S3 SCENARIO: Your nightly batch job processes 50,000 records. After processing 30,000 records,

the app restarts. How do you ensure it continues from record 30,001?

✅ Complete Scenario Answer

Solution: Watermark + persistent ObjectStore

End-to-End Architectural Execution & Error Trace
1. In Load & Dispatch: read watermark from persistent ObjectStore → SELECT * FROM accounts WHERE
updatedAt > :lastWatermark ORDER BY updatedAt
2. For each batch, update watermark to the last processed record's updatedAt timestamp
3. On restart: Load & Dispatch reads watermark → queries only records AFTER last-processed
timestamp → continues from record 30,001
4. On Complete: update watermark with final timestamp for next run
Interview Drill-Down & "What If?" Cross-Questions
"What if updatedAt has the same value for multiple records?" — Use record ID as secondary

• watermark. Or use a dedicated processed=true column — mark each record processed immediately,

• restart queries only WHERE processed=false .

"Mule Batch Job claims to be persistent — why do you need an external watermark?" — Mule

• batch persistence tracks the current job instance's progress. But it resets when a NEW job instance

• starts. The watermark persists across job instances — it's the source-system filter, not just job state.

"What if the app crashes during the watermark update?" — The watermark reflects the last fully

• committed batch. A few records may be reprocessed on restart. They're handled by UPSERT

• idempotency in the target system — no duplicates created.

• 🔹 Scenario Set 3: Data Consistency Scenarios
S6 S6 SCENARIO: Your flow inserts a record into DB, then publishes to Anypoint MQ. The DB insert

succeeds but MQ publish fails. What happens? How do you prevent this?

✅ Complete Scenario Answer

What happens without protection: DB record exists, MQ message never published →

downstream consumer never processes it → inconsistent state (DB has record, no event fired).

Solutions:

Transactional Outbox Pattern: DB insert + MQ publish in same XA transaction. If MQ publish

fails → entire transaction rolls back → DB insert undone. Requires XA-capable DB + JMS

(Anypoint MQ doesn't support XA).

Transactional Outbox in DB: Write event to an outbox table in the same DB transaction as

the main insert. A separate Scheduler flow polls the outbox table → publishes to MQ → deletes

from outbox. Guaranteed delivery because it's one DB transaction.

Retry on MQ failure: Use Until Successful wrapping the MQ publish. If all retries fail →

compensate by deleting the DB record (rollback manually). Log the failure with correlationId

for reconciliation.

Interview Drill-Down & "What If?" Cross-Questions
"Does Anypoint MQ support XA transactions?" — No. Anypoint MQ uses MANUAL ack pattern

• instead. For DB + MQ atomicity, use the Transactional Outbox pattern in DB, OR accept eventual

• consistency with retry + idempotency.

"What if the reverse happens — MQ publishes but DB fails?" — Same problem in reverse.

• Solution: write to DB first, then publish to MQ. If MQ fails → retry MQ (data is already in DB safely). If

• DB fails → never reach MQ publish.
S7 S7 SCENARIO: Salesforce sends the same Platform Event twice due to at-least-once delivery. Your

flow creates a record in SAP both times. How do you prevent duplicate SAP records?

✅ Complete Scenario Answer

Three-layer defense:

  • 1. ObjectStore idempotency check: Extract the Salesforce Event's replayId or business key

(Opportunity ID). Check ObjectStore: if EXISTS → skip and log "Duplicate event". If NOT EXISTS

→ process → store key with TTL=72h.

  • 2. SAP UPSERT instead of CREATE: Configure the SAP call to use UPSERT semantics (check-and-

create). SAP checks if the record already exists by external key before creating. Even if

duplicate reaches SAP, SAP returns existing record instead of creating new one.

  • 3. Use MANUAL ack mode: Only ACK the event after successful ObjectStore write + SAP call. If

anything fails before ACK, event is redelivered. Combined with idempotency, retries are safe.

Interview Drill-Down & "What If?" Cross-Questions
"What TTL should you set on the idempotency key?" — TTL should be slightly longer than

• Salesforce's event retention (72 hours). Set TTL=73h or 25h for MQ. If the same event could arrive

• after 72h (very unusual), the system would re-process, which is acceptable.

"What if two workers receive the same event simultaneously?" — ObjectStore v2 uses atomic

• operations. The os:contains + os:store are not atomic. Use os:retrieve-and-store (atomic CAS

• operation) to handle race conditions between workers.

✅ Complete Scenario Answer

sub-flow instead of a private flow. An error inside the sub-flow is NOT caught by the sub-flow —

it propagates up to the calling flow's error handler. The calling flow handles a different kind of

error that the sub-flow was supposed to handle locally. Result: wrong error response returned.

Fix: Use a private flow instead of sub-flow when you need independent error handling scope.

Reverse bug: You use a private flow for simple code reuse. The private flow runs in its own

transaction context. If the calling flow has a XA transaction, the private flow is NOT part of that

transaction. DB writes inside the private flow won't roll back when the calling flow's transaction

fails.

Fix: Use sub-flow for transactional operations that must be part of the calling flow's transaction.

D2 D2 Interviewer: "Why did you use Scatter-Gather here? Couldn't you just call them sequentially?"

✅ Design Decision Explanation

"Great question. I asked the same thing before implementing it.

one). That's a 20% reduction on the happy path.

amount from SAP doesn't affect what preferences to fetch from DynamoDB. They don't depend on each

other. When you have independent parallel sources, Scatter-Gather is the right tool.

Sequential calls make sense when one call's output IS the input to the next — like fetching an accountId

from Salesforce and then using that ID to query SAP. In that case there IS a dependency, so Scatter-

Gather doesn't help.

Does that address the design choice?"

"Error handling is one of the most important parts of the design — it's easy to get happy path right,

builds a standardized error payload — correlationId, errorCode like 'SAP_ERROR', description, layer —

and re-throws it using on-error-propagate.

The PAPI receives this error. It doesn't try to handle it — it enriches it with PAPI context and propagates

response. It maps the error to the correct HTTP status: SAP unavailable → 503, bad request → 400, not

The key principle: every API in every layer has the same error response shape — same JSON keys,

same structure. This means the XAPI always knows what to expect regardless of where the error

originated."

DSS compliance. How do you architect it?

This scenario tests your ability to combine security, performance, and compliance in a real-world

banking context.

Architecture layers:

Experience API (XAPI): Mobile/web-facing HTTPS endpoint. Enforces OAuth 2.0 + JWT. Rate limited

to 10,000 req/min per client ID via API Manager SLA tiers. No business logic at this layer.

Process API (PAPI): Transaction orchestration. Validates payload against JSON Schema. Deduplication

via idempotent receiver (ObjectStore). Enriches with account data from SAPI. Publishes to Anypoint

MQ for async downstream processing.

System API (SAPI): Core banking adapter. Connects to Temenos/FIS via secure mTLS. No PAN (card

numbers) stored in Mule variables — pass-through to vault only.

PCI-DSS compliance controls:

Encryption: TLS 1.2+ on all HTTP connections; field-level encryption for PAN data via Anypoint

Secrets Manager or AWS KMS

Tokenization: Card numbers replaced with tokens before entering Mule flows — Mule never stores

raw PANs

Audit logging: Every request logged with correlation ID, user ID, timestamp, masked data — to

Splunk SIEM via async logger

Network segmentation: Runtime Fabric deployed in isolated VPC; no public internet access to SAPI

layer

Secret management: All credentials in Anypoint Secrets Manager — never in property files

committed to Git

Performance for 10K TPS: CloudHub 2.0 auto-scaling + Anypoint MQ as buffer (XAPI → MQ → PAPI)

decouples ingestion rate from processing speed. MQ absorbs burst traffic; PAPI processes at

sustainable rate.

Interview close: I would validate this design against MuleSoft API-led connectivity reference

architecture, Anypoint Security checklist, and PCI-DSS requirements 6.4 and 10.
