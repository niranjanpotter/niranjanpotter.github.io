Q1 [SENIOR / LEAD] ⏱️ 1 min read Module Q

Describe your Billing Inquiry flow end to end.

⚡ Self-Test Mode Ready
✓ ANSWER

📋 BILLING INQUIRY FLOW — GET /BILLING/INQUIRY

1.Salesforce Employee Desktop calls customer-billing-xapi with OAuth token
2.XAPI validates Client ID policy → calls billing-inquiry-papi
3.PAPI uses Scatter-Gather to call SAP Billing SAPI + DynamoDB Preferences SAPI in parallel
4.SAP SAPI: HTTP OData call → returns XML with billing details, charges, contract info
5.DynamoDB SAPI: HTTP + SigV4 → returns customer display preferences
6.DataWeave merges both: maps SAP XML → JSON + overlays DynamoDB preferences
7.Result: response time reduced from 2.5s → 1.1s = 55% improvement
Q2 [SENIOR / LEAD] ⏱️ 1 min read Module Q

What was the most challenging technical problem you solved?

⚡ Self-Test Mode Ready
✓ ANSWER

Problem: SAP Billing Inquiry returned XML where the ToInstallations node could be empty for

accounts with status "Pending Final + Disconnected" causing NullPointerException in production.

Fix: Added null-safe DataWeave with default [] and default "UNKNOWN" for all SAP array/string

nodes. Added a MUnit test for this edge case — never regressed in 18 months. Lesson: always use

default for SAP XML nodes.

Q3 [SENIOR / LEAD] ⏱️ 1 min read Module Q

How did you manage the async preference update flow?

⚡ Self-Test Mode Ready
✓ ANSWER

📋 PREFERENCE UPDATE — ASYNC PATTERN

1.Mobile app calls preference-update-xapi → XAPI validates + publishes to Anypoint MQ → returns 202 Accepted
2.MQ consumer picks up → checks ObjectStore for transactionId (idempotency)
3.EXISTS: ACK + skip. NOT EXISTS: write to DynamoDB + Salesforce
4.On success: os:store(transactionId, TTL=24h) + anypoint-mq:ack
5.On failure: anypoint-mq:nack → returned to queue for retry
6.Prevented 47 duplicate DynamoDB writes in first month of production
🎯🎯 Interview Pitch - Say It Like This (30 Sec)
"I use Choice Router for content-based routing where deterministic DataWeave expressions evaluate which single execution path to take, always configuring a default route for unhandled exceptions. In contrast, First Successful is ideal for active-passive failover—attempting a primary API route first, and only trying the secondary backup if an error is thrown."
💼💼 Real-Time Project Example

Project: Aviation — Multi-Carrier Shipping Rate Dispatcher.

Problem: Hardcoded if-else routing logic led to maintainability nightmares and complete order failure when the primary shipping partner API went down.

What I Did: Implemented a Choice router for package size rules, combined with a First Successful scope attempting primary carrier API first, falling back to secondary carrier.

Result: Reduced shipping dispatch errors by 100% and guaranteed zero order checkout interruptions during partner carrier outages.
