Q1 [DEVELOPER] ⏱️ 1 min read Module G

What is Scatter-Gather? How does it work?

⚡ Self-Test Mode Ready
✓ ANSWER

Scatter-Gather clones the incoming Mule Event across all defined routes, executes them concurrently on parallel threads, and waits for all branches to finish. After all routes complete, results are aggregated into an Object (indexed Map) keyed by route index ("0", "1", "2"), where each value is that route's resulting Mule Message ({ payload, attributes }).

💡 KEY RUNTIME BEHAVIOR: Output is an Object (Map), not an Array. Access individual route payloads by key (payload."0".payload or positional payload[0].payload) or flatten all route payloads with flatten(payload..payload) / valuesOf(payload).payload. Total execution latency equals the slowest route, and variables (vars) modified in non-conflicting routes merge back into the main flow afterward (conflicting variable names merge into an Array).

🎯🎯 Interview Pitch - Say It Like This (30 Sec)
"When an API orchestration requires parallel data fetching from multiple disparate backends, I implement the Scatter-Gather router. It invokes all routes concurrently on separate threads and aggregates responses into an indexed Map. I always wrap individual routes in Try scopes or inspect MULE:COMPOSITE_ROUTING to ensure that a failure in one non-critical route does not fail the entire customer response."

Q2 [DEVELOPER] ⏱️ 1 min read Module G

What is the output type of Scatter-Gather? How do you merge results?

⚡ Self-Test Mode Ready
✓ ANSWER

The output of Scatter-Gather in Mule 4 is an Object (indexed Map) whose keys are string route indices ("0", "1", "2"...). Each entry contains a full Mule Message with payload (that route's output payload) and attributes (protocol metadata such as HTTP status code and headers). To merge all routes dynamically into a single array, use flatten(payload..payload).

Q3 [DEVELOPER] ⏱️ 1 min read Module G

If one route in Scatter-Gather fails, what happens to the others?

⚡ Self-Test Mode Ready
✓ ANSWER

By default: if any route fails, Scatter-Gather throws a MULE:COMPOSITE_ROUTING error and the results

of all routes (including successful ones) are discarded.

To handle partial failures: wrap each route in a scope with an on-error-continue . This captures

the error within that route without propagating it to Scatter-Gather. The successful routes continue

normally and return their results.

Scatter-Gather with per-route error handling

{error: error.description}

💬 CROSS-QUESTIONS INTERVIEWERS ASK ABOUT THIS TOPIC

"What if ALL 3 routes fail?" → With Try scope: all 3 attempt, all return error objects. Scatter-Gather

aggregates all 3. Without Try scope: first failure cancels everything → MULE:COMPOSITE_ROUTING. Best

practice: Try scope per route, check result[N].payload.error != null after.

"What if SAP takes 5 seconds — what is total Scatter-Gather time?" → 5 seconds. Total time =

SLOWEST route. DynamoDB finishes in 200ms but must wait for SAP. Fix: set timeout on Scatter-Gather

element. After timeout: MULE:TIMEOUT — use partial results from routes that completed.

"Is the result array ordered the same as the routes?" → YES. payload[0] = first route, payload[1] =

second route, regardless of which finished first. Order is always design-time route order.
