Q1 [DEVELOPER] ⏱️ 1 min read Module N

What is ObjectStore? What are the types?

⚡ Self-Test Mode Ready
✓ ANSWER

ObjectStore is a key-value store built into Mule for persisting state between executions. Used for

watermarking, idempotency, caching, and session management.

TYPEPERSISTENCEUSE FOR
In-Memory (default)Lost on app restart or redeployShort-term caching, temporary state within session
PersistentSurvives app restarts (stored to disk/CloudHub OS)Watermarks, idempotency keys, long-term state
Anypoint OS v2 (CloudHub)Survives restarts AND scales across workersProduction idempotency in multi-worker deployments
ℹ️Important
In CloudHub with 2+ workers, use Anypoint Object Store v2 (persistent=true) — each

worker has its own in-memory OS. Without v2, idempotency keys stored on worker 1 are not visible

to worker 2.

ℹ️2025-2026 Core Concept Verification · ObjectStore v2 Behavior
• TTL & Expiration: Default entry TTL is 30 days if unspecified, or user-configurable (e.g., 300s for cache, 24h for idempotency). Expiration job runs asynchronously every 300 seconds.
• CloudHub 2.0 Multi-Replica Behavior: Replicas in Private Spaces are independent Kubernetes pods. In-Memory stores are strictly container-local and destroyed on restart/reschedule. Setting persistent=true routes state to the managed Anypoint ObjectStore v2 service backed by AWS DynamoDB in the tenant's region, enabling full cross-replica state synchronization.
• Service Limits: 10 MB max Base64-encoded value size per key (256-char max key length) with unlimited total keys/storage per app, 30-day max TTL (rolling on read/write), and 10 TPS per app on standard OSv2 tier (upgradable to 100 TPS per app with Titanium / Premium OSv2 add-on).

This guarantees that state is synchronized across all multi-replica pods via AWS DynamoDB with an explicit TTL, preventing duplicate processing even during sudden pod restarts."

Q2 [DEVELOPER] ⏱️ 1 min read Module N

What is watermarking? How does ObjectStore store watermark values?

⚡ Self-Test Mode Ready
✓ ANSWER

Watermarking tracks the last-processed position (timestamp, ID, sequence number) so a scheduled

job only processes new/changed records since the last run.

Watermark Pattern — Nightly SAP Sync

DWL 
// In Load & Dispatch phase:
// 1. Read last watermark from ObjectStore
// 2. Use watermark in SAP query
// WHERE LastModifiedDate > :lastWatermark
// In On Complete:
// 3. Update watermark with current run timestamp
#[now()]

In our Enterprise Architecture: watermark persisted in Anypoint OS v2 (persistent=true, no TTL). Nightly SAP account sync

processes only accounts modified since last run — instead of full 50K record scan, typically processes

only 500-2000 changed records per night.

ℹ️2025-2026 Production Best Practice · Watermarking Safety
• Commit Timing: Always update the watermark in the persistent ObjectStore at the very end of the flow after successful downstream ingestion. Updating before processing causes silent data loss if an error occurs mid-stream.
• Overlap Window: In high-volume CDC syncs, subtract an overlap buffer (e.g. now() - |PT5M|) to catch records with delayed database commit timestamps, relying on downstream idempotency or External ID upserts to discard duplicates.
