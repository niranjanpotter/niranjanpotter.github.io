Q1 [DEVELOPER] ⏱️ 2 min read Module J

What is Until Successful? When do you use it?

⚡ Self-Test Mode Ready
✓ ANSWER

Until Successful retries the processors inside it until they succeed or until the max retries count is

reached. Use for transient failures — network blips, temporary backend unavailability.

Until Successful — Retry SAP call 3 times

✅ KEY CONFIGURATION

maxRetries : Number of retry attempts (default: 5). Does NOT include the initial attempt.

millisBetweenRetries : Wait time between retries (default: 60000ms = 1 minute)

On exhaustion: throws MULE:RETRY_EXHAUSTED — catch in error handler

💬 CROSS-QUESTIONS INTERVIEWERS ASK ABOUT THIS TOPIC

"You set maxRetries=3 — how many total attempts happen?" → 4 total. maxRetries counts retries

AFTER the initial attempt. 1 initial + 3 retries = 4 total. Common interview trap — many say "3 attempts."

"Does Until Successful support exponential backoff?" → No built-in exponential backoff.

millisBetweenRetries is a fixed delay between every retry. To implement exponential backoff you'd need a

custom pattern (set a variable that doubles the delay). The reconnection strategy on connectors has

exponential backoff — Until Successful does not.

"Should you use Until Successful to retry a 400 Bad Request from SAP?" → No. 400 is a client error —

the request itself is wrong. Retrying the same request will always get the same 400. Only retry transient

errors: 5xx, timeouts, connectivity failures. Add a condition to skip non-retryable errors: wrap in Try scope

and only re-throw 5xx errors.

"What is the default millisBetweenRetries?" → 60,000ms (1 minute). The default means 5 retries × 1

minute = 5 minutes before exhaustion. In production we always override this to a shorter value (5000ms)

for fast-fail behavior.

🎯🎯 Interview Pitch - Say It Like This (30 Sec)
"In enterprise integrations, I clearly distinguish between Until Successful and Reconnection Strategy. Reconnection strategies handle initial or broken TCP socket connections at the connector level. In contrast, Until Successful is an active flow-level router that retries business processor execution for transient HTTP 5xx errors or timeouts with exponential backoff and a hard max retry count."
💼💼 Real-Time Project Example

Project: Energy & Utility — External Payment Gateway Connector.

Problem: Intermittent 200ms network glitches on third-party payment partner endpoints caused 4% of customer checkout requests to fail immediately.

What I Did: Wrapped the HTTP Request in an Until Successful scope configured with 3 retries, a 2000ms delay, and exponential backoff, failing over to a DLQ on exhaustion.

Result: Automatically self-healed 99.4% of transient failure attempts without customer impact, saving approximately 1,200 orders per week.

Q2 [DEVELOPER] ⏱️ 1 min read Module J

What happens when Until Successful exhausts all retries?

⚡ Self-Test Mode Ready
✓ ANSWER

When all retries are exhausted, Until Successful throws MULE:RETRY_EXHAUSTED . This error bubbles up

to the flow's error handler (or the enclosing scope's error handler).

In our Enterprise Architecture: we catch MULE:RETRY_EXHAUSTED in the flow error handler → update Salesforce with

SAP_Error_Status__c = 'FAILED' → send Anypoint Alert to operations team → publish failed message

to DLQ for manual reprocessing.
