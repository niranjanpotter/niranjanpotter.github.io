Q2 [DEVELOPER] ⏱️ 1 min read Module B

What is Salesforce Bulk API? When do you use it?

⚡ Self-Test Mode Ready
✓ ANSWER

Bulk API 2.0 loads or extracts millions of records asynchronously and does NOT consume your org's standard REST/SOAP 24-hour rolling API request allocation (100,000 base + 1,000 per license in Enterprise Edition). (Note: 150 is the Apex synchronous DML statements-per-transaction limit, not the REST API call quota.)

Bulk API 1.0 vs 2.0: Bulk 1.0 (XML/CSV) requires explicit batch creation (10,000 records/batch). Bulk API 2.0 uses CSV with single uploads up to 150 MB base64-encoded (~100 MB raw), auto-chunks batches behind the scenes, and provides a dedicated 15,000 batches / 150M records per 24-hour quota — always choose 2.0 for new integrations.

✅ BULK API BEST PRACTICES

Use Upsert Bulk with External ID (SAP_Customer_ID__c) for idempotency on retry

Retrieve job results in On Complete phase — store failures in S3/DLQ for review

Batch Aggregator batch size = 5,000 for optimal Salesforce batch throughput

Results retained 7 days — always persist your own failure logs

Q3 [DEVELOPER] ⏱️ 1 min read Module B

How do you handle Salesforce governor limits?

⚡ Self-Test Mode Ready
✓ ANSWER

Standard REST/SOAP API Limit (Enterprise Edition): Rolling 24-hour org quota of 100,000 base calls + 1,000 calls per Salesforce user license (Sandboxes allow up to 5,000,000 calls per 24 hours — not unlimited; note that 150 is the Apex synchronous DML limit per transaction, not REST API calls/hour). Key mitigations:

Bulk API 2.0 — uses a separate 150M records / 15,000 batches per 24h pool so it does NOT exhaust standard REST/SOAP API quotas

ObjectStore caching — cache frequently-read SF data with TTL=5min

Platform Events/CDC — event-driven instead of polling reduces calls

queryMore — for large SOQL results, paginate instead of multiple queries

🎯🎯 Interview Pitch - Say It Like This (30 Sec)
"When integrating with Salesforce, governor limits are top of mind. Rather than performing individual synchronous REST calls, I architect integrations using the Bulk API v2 for large datasets, cache reusable reference data in ObjectStore v2, and leverage Platform Events for event-driven asynchronous processing to keep daily API consumption well below 40% of allocated limits."
💼💼 Real-Time Project Example

Project: Aviation — High-Volume Customer Account Synchronization.

Problem: Synchronous individual REST calls were consuming 85% of Salesforce's 24-hour API limit by mid-day, threatening to block production transactions.

What I Did: Implemented Batch Processing in MuleSoft with a Batch Aggregator of 200 records calling Salesforce Composite and Bulk API v2.

Result: Reduced daily Salesforce API consumption from 95,000 calls to under 8,500 calls (a 91% reduction) with zero limit breaches.

Q4 [DEVELOPER] ⏱️ 1 min read Module B

JWT Bearer vs Username-Password auth for Salesforce — which do you use?

⚡ Self-Test Mode Ready
✓ ANSWER

Username-Password: requires actual user credentials. Password changes break integration, account

can lock, appears as user in audit logs — never use in production.

JWT Bearer: RSA asymmetric key pair — no password needed. Token signed by MuleSoft private key,

validated by Salesforce with uploaded public key. Survives password changes, cleaner audit trail

showing Connected App not a user.

⚠ ALWAYS USE JWT BEARER IN PRODUCTION

Generate RSA key pair → upload public cert to Connected App in Salesforce Setup

Store keystore.jks as Secure Property (AES-CBC encrypted) in CloudHub

Rotate keys: upload new cert BEFORE removing old one (zero-downtime rotation)

🎯🎯 Interview Pitch - Say It Like This (30 Sec)
"For secure system-to-system integrations with Salesforce or third-party gateways, I mandate OAuth 2.0 JWT Bearer flow. It completely eliminates storing username/passwords or interactive user approvals. We sign a JWT claim with an RSA private key stored securely in the keystore, and exchange it for a short-lived access token, managing key rotation seamlessly with dual certificates."
💼💼 Real-Time Project Example

Project: Energy & Utility — Automated Headless Microservice Authentication.

Problem: Legacy integrations used hardcoded service account passwords that broke every 90 days due to corporate password expiration policies.

What I Did: Re-architected authentication to Salesforce Connected App using OAuth 2.0 JWT Bearer Token flow with a 2048-bit digital certificate stored in JKS keystore.

Result: Achieved 100% automated headless authentication with zero password maintenance outages and passed corporate SOC2 security audits.

Q5 [DEVELOPER] ⏱️ 1 min read Module B

What is an External ID in Salesforce? How is it used in Upsert?

⚡ Self-Test Mode Ready
✓ ANSWER

A custom field with "External ID" checkbox enabled in Salesforce Setup. Stores source system ID (SAP Customer Number). For Upsert: Salesforce finds records matching this field — found → update, not found → insert.

In MuleSoft: set externalIdFieldName="SAP_Customer_ID__c" on the Upsert operation. Makes integrations safe to retry without creating duplicates.

🎯🎯 Interview Pitch - Say It Like This (30 Sec)
"In enterprise integrations, I enforce using Salesforce External IDs paired with the Upsert operation as a best practice for idempotency. This allows MuleSoft to create or update records in a single transactional call based on the enterprise key (such as SAP Customer Number or Account ID), eliminating the need for expensive 'Query before Insert' lookups and preventing duplicate record creation."
💼💼 Real-Time Project Example

Project: Retail & E-Commerce — Bidirectional Customer Master Data Sync.

Problem: Network retries caused duplicate account records to be created in Salesforce when downstream ACKs were delayed.

What I Did: Configured an External ID field `SAP_Customer_Number__c` in Salesforce and executed Upsert operations directly from the MuleSoft Salesforce connector.

Result: Eliminated 100% of duplicate account records and improved API throughput by 35% by skipping preliminary SOQL lookups.
