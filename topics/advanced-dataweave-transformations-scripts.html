Explain mTLS. How do you debug mTLS-related issues?

⚡ Self-Test Mode Ready
✓ ANSWER

mTLS (Mutual TLS): Both client and server authenticate each other using certificates. Unlike one-way

SSL where only the server presents a cert, in mTLS the client ALSO presents a certificate to the server

for verification.

MuleSoft configuration:

mTLS configuration in HTTP Request

📋 MTLS DEBUGGING STEPS

1.Check certificates are valid and not expired: openssl x509 -in cert.pem -text -noout
2.Verify trustStore has the server's CA certificate
3.Verify keyStore has the client's private key + certificate chain
4.Check TLS version match — both ends must support the same TLS version (1.2+)
5.Review server logs for handshake failures: "Received fatal alert: certificate_unknown"
6.Test with openssl: openssl s_client -connect host:443 -cert client.pem -key key.pem

Q3 [SENIOR] ⏱️ 1 min read Module V

What is the difference between Rate Limiting, Spike Control, and Throttling?

⚡ Self-Test Mode Ready
✓ ANSWER
POLICYBEHAVIOR WHEN LIMIT EXCEEDEDUSE CASE
Rate LimitingRequest is REJECTED immediately (HTTP 429)Prevent abuse — hard limit per client per time window
Spike ControlRequest is QUEUED and processed when capacity availableHandle burst traffic — temporarily buffer excess requests
ThrottlingRequest is SLOWED DOWN (delayed response)Gradual degradation — same as rate limiting but with delay instead of rejection

💡 EXAMPLE

Rate Limiting: "You can only make 100 requests per minute. Request 101 = 429 Too Many Requests." Spike

Control: "You can only make 100 requests per minute, but I'll queue the extras and process them as capacity

frees up." Throttling: "You're making too many requests, so I'll slow down my responses to manage load."

⚡ Self-Test Mode Ready

Transaction management ensures a group of operations execute as a single unit of work — either all

succeed or all are rolled back.

Q5 [SENIOR] ⏱️ 1 min read Module V

What is guaranteed delivery? How do you ensure it in MuleSoft?

⚡ Self-Test Mode Ready
✓ ANSWER

Guaranteed delivery ensures messages are reliably delivered even if the system crashes or restarts.

MuleSoft achieves this through:

📋 GUARANTEED DELIVERY PATTERN

Persistent Queues: Anypoint MQ stores messages on disk — survives app restart (7-day retention)

MANUAL Acknowledgement: Message NOT removed from queue until explicitly ACKed after successful processing

NACK on failure: Failed messages returned to queue for retry — not permanently lost

DLQ (Dead Letter Queue): Messages that exceed max retries go to DLQ for manual review/reprocessing

Idempotency: ObjectStore prevents duplicate processing when message is redelivered after retry

✅ GUARANTEED DELIVERY = PERSISTENT MQ + MANUAL ACK + NACK + DLQ + IDEMPOTENCY
