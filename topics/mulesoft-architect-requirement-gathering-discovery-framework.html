R1 [ENTERPRISE ARCHITECT] ⏱️ 3 min read Module DD

How do you run discovery for a new integration? What framework do you follow?

⚡ Self-Test Mode Ready
✅ Architect Answer

I use an 8-part discovery framework. I don't start design until every part has an owner and either

an answer or a written assumption.

#AREAWHAT I NEED TO LEAVE THE ROOM WITH
1Business goalThe outcome in business terms ("orders reach SAP within 5 minutes so the warehouse can ship same day"), not "build an API".
2StakeholdersSponsor, product owner, owner of every source/target system, security, operations/support, UAT sign-off.
3SystemsEach system, its interface (REST, SOAP, OData, JDBC, file, JMS/MQ), environment availability, who provides credentials.
4DataEntities, formats, average and peak volumes, system of record per field, PII/PCI/PHI classification.
5NFRsLatency, TPS, availability, RPO/RTO, retention, sync vs async tolerance.
6SecurityAuth per system, network path (VPN, private space, firewall), encryption, compliance (GDPR, HIPAA, PCI-DSS, SOX).
7ConstraintsBudget, deadlines, licence capacity (vCores/flows/messages), mandated platforms, blackout windows, team skills.
8Success criteriaMeasurable acceptance, e.g. "99.5% of orders posted within 5 minutes during a 2-week hypercare".
✅ SAY THIS IN THE INTERVIEW

"Before I draw a single box I need three answers: the business outcome, the system of record for each

field, and the peak volume. Those decide most of the architecture."

✅ Exact Words to Say · 🎤 SAMPLE BEST ANSWER — SAY IT LIKE THIS
""When I start a new integration, I don't open Studio first. I run discovery across eight areas:
business goal, stakeholders, systems, data, NFRs, security, constraints and success criteria. For
example, if the client says 'sync orders to SAP', I'll ask what business outcome they want. Usually
it's something like 'warehouse ships same day', which tells me five minutes is fine and I can go
async. I write every answer, or every assumption, into a RAID log and get it signed off. That way
design is driven by requirements, and there are no surprises in UAT.""
🎯🎯 Interview Pitch - Say It Like This (30 Sec)
"When leading integration discovery workshops, I follow a structured four-pillar framework: Business Objectives, Technical Architecture, Data Contracts & Volume, and Non-Functional Requirements (SLAs, Security, DR). I actively probe for edge cases—like downstream downtime behavior, peak TPS, and data purge policies—to de-risk the delivery before design begins."

Project: Healthcare — Enterprise Solution Scoping & Workshop.

Problem: Client stakeholders had vague requirements for a multi-system sync, resulting in unstated expectations around data freshness and high failure rates.

What I Did: Facilitated a 2-day discovery workshop using an integration checklist, mapping source-to-target data flows, error response schemas, and peak volume requirements.

Result: Delivered signed off technical design documents with zero scope disputes and reduced implementation re-work by 40%.

What questions do you ask the client, by category?

⚡ Self-Test Mode Ready
✅ Architect Answer — Question Bank
CATEGORYQUESTIONS TO ASK
Business OutcomesWhat problem costs time or money today? Which steps are manual? What happens if delivery slips, and what does "done" look like?
Systems & EndpointsWhich systems are source and target? API vs DB/file access? Is there an Exchange connector, sandbox per environment, owner, and change calendar?
Data Volume & FormatsDaily & peak-hour record volumes? Largest single payload size? Formats (JSON, XML, CSV, IDoc, EDI, fixed-width)? Authoritative System of Record & historical backfill needs?
SLA / TPS / LatencySynchronous user wait vs asynchronous eventual consistency? P95 latency target? Peak TPS spikes (month-end, flash sales)? Uptime SLA & maintenance windows?
Security & ComplianceOAuth 2.0, mTLS, API key, or SAML? PII/PCI/PHI scope? Data residency & Private Space / VPC isolation? Audit log retention rules?
Error Handling & RetriesWhen downstream is unavailable: retry, queue to DLQ, alert, or reject? Are targets idempotent? Who remediates & replays failed messages?
Monitoring & OpsAlert routing (PagerDuty, ServiceNow, Teams)? Existing APM/log platform (Splunk, Datadog, ELK)? Required business & SLA dashboard KPIs?
Deployment & CI/CDCloudHub 2.0 (Shared vs Private Space), RTF on K8s, or Hybrid? Target regions, CI/CD pipeline tooling, and production change-approval gates?
API GovernanceNaming & URI versioning rules? Automated Anypoint API Governance rulesets? Exchange publishing workflow & standard layer policies (Client ID, JWT, Rate Limit)?
🎤Sample Architect Answer — Say It Like This
"I group discovery questions across 9 dimensions so nothing gets missed: Business outcomes first, then Systems, Data volume/format, SLAs/TPS, Security, Error recovery, Monitoring, Deployment topology, and Governance. The three answers that shape architecture fastest are peak TPS, 'is a caller waiting synchronously?', and 'which system owns the truth when records disagree?' I share the checklist 48 hours ahead so workshops drive decisions rather than raw fact-finding."

R3 [ENTERPRISE ARCHITECT] ⏱️ 2 min read Module DD

What red flags do you watch for in discovery, and which assumptions do you confirm in

⚡ Self-Test Mode Ready

writing?

✅ Architect Answer

🚩 Red flags

"Real-time" with no latency number

No named owner for a source or target system

Target system has no test environment

"Volumes are small" with no data behind it

Credentials or firewall changes "sorted later"

Business rules exist only in someone's head or unreadable legacy code

Go-live date fixed before scope is known

Bidirectional sync with no agreed system of record

📝 Assumptions to confirm in writing

Peak TPS and payload size used for sizing

Target APIs are idempotent (or we add a dedupe store)

Client provides network connectivity by date X

Data cleansing is the client's responsibility

Out of scope: reporting, historical migration, UI changes

Environments: DEV, QA/SIT, UAT, PROD

A named support team takes alerts after hypercare

⚠️⚠️ Production Warning · ⚠ WHY IT MATTERS
Every unconfirmed assumption becomes a change request later. Put them in the solution design
document and get them signed off with the scope.
✅ Exact Words to Say · 🎤 SAMPLE BEST ANSWER — SAY IT LIKE THIS
""My biggest red flag is a word like 'real-time' with no number attached. Others are a system with
no owner, no test environment, or a fixed go-live before scope is known. Each one goes into the
RAID log as a risk with an owner. And I write my assumptions down, for example peak TPS,
idempotent targets and who cleans data, and get them signed with the scope. In my experience,
unwritten assumptions are where most change requests come from.""

What "delighters" do you add to make the client happy beyond the core integration?

⚡ Self-Test Mode Ready
✅ Architect Answer

Delighters are cheap extras that lower the client's risk and effort. I put them in the estimate from

day one so they don't get cut at the end.

DELIGHTERWHY THE CLIENT CARES
Exchange API Portal DocsConsumers self-serve specs and examples, cutting "how do I call this?" support tickets
Design Center Mock ServicesFrontend and partner teams build in parallel before backend APIs are completed
Postman / Insomnia CollectionsPre-configured per environment so QA and support reproduce calls in minutes
MUnit Coverage & Quality ReportAuditable proof of automated regression safety for future releases
Proactive Dashboards & AlertsAnypoint Monitoring / Splunk / Datadog alerts notify Ops before business users notice issues
L1/L2 Operations RunbooksSupport can restart pods, triage DLQs, and replay events without escalating to build teams
Reusable Accelerator TemplatesShared parent POM, JSON logger, and global error handler accelerate subsequent APIs
Automated CI/CD PipelineRepeatable, zero-manual-error, fully auditable deployments across environments
Load & Performance EvidenceJMeter / k6 test proof validating SLA compliance under peak TPS projections
Security Sign-Off ChecklistFaster InfoSec approval with documented TLS, OAuth, mTLS, and PII log masking proof
Phase-2 Reuse RoadmapHighlights next high-ROI integration candidates where existing SAPIs can be reused
Recorded KT & vCore Cost ReviewClient team can run operations independently with right-sized vCore/replica licensing

Give me your requirements checklist (copy-friendly).

⚡ Self-Test Mode Ready
✅ Copy-Friendly Checklist

requirements-checklist.txt

  • Business goal stated as a measurable outcome
  • Sponsor, product owner and system owners named
  • Source and target systems listed with interface type
  • Test environment confirmed for every system
  • Data entities, formats and field mappings drafted
  • System of record agreed per entity/field
  • Average and peak volume, max payload size
  • Sync vs async decided per interface
  • Latency (p95) and TPS targets
  • Availability, RPO and RTO
  • Auth method and credential owner per system
  • Network path (public, VPN, private space, private link)
  • Data classification (PII / PCI / PHI) and masking rules
  • Compliance and data residency requirements
  • Error handling, retry policy, DLQ and replay process
  • Idempotency approach for every write
  • Alert recipients and channels
  • Logging platform and retention
  • Deployment target (CloudHub 2.0 / RTF / hybrid) and region
  • CI/CD tool and release approval process
  • API naming, versioning and governance rules
  • Out-of-scope list signed off
  • Assumptions and RAID log signed off
  • Acceptance criteria and UAT owner
  • Hypercare length and handover-to-support plan

R7 [ENTERPRISE ARCHITECT] ⏱️ 2 min read Module DD

Mini case study: Salesforce → SAP → Database order sync. How would you gather

⚡ Self-Test Mode Ready

requirements and shape the solution?

✅ Illustrative Case Study (not a real client)

Ask: "When a Salesforce Opportunity is Closed Won, create a sales order in SAP S/4HANA and

store the order status in a reporting database."

📋 DISCOVERY FINDINGS (ILLUSTRATIVE)

Business goal: order in SAP within 5 minutes so the warehouse ships same day

Volume: about 2,000 orders/day; month-end peak about 10x for 2 hours

Salesforce owns customer and deal data; SAP owns order number and status

SAP exposes an OData sales order API; the reporting DB is PostgreSQL

SAP has a weekly maintenance window, and no order may be lost during it

Customer address is PII; finance wants a daily reconciliation report

Resulting design: Salesforce Platform Event / CDC → Order PAPI → Anypoint MQ queue (absorbs

SAP downtime and the month-end peak) → SAP SAPI (OData create, idempotent on the

Opportunity ID) → write the SAP order number back to Salesforce → DB SAPI upsert. DLQ plus a

replay runbook for failures, and a nightly reconciliation flow comparing Closed Won opportunities

with SAP orders.

✅ HOW EACH REQUIREMENT DROVE A CHOICE

"5 minutes, not instant" → async through MQ is acceptable

"Weekly SAP window" → queue and retry instead of failing the user

"System of record per field" → prevents the update loop (see Section F, Q2)

"Finance wants reconciliation" → the reconciliation flow is in scope from day one
